# Tsuzunowa v0.2.0-alpha.2

Released 2026-11-27. An alpha **source preview** for the self-hosted Web app and
API, with Tsuzunowa's approved name, icon and wordmark. This is an independent
Colanode fork, not an official Colanode release. Earlier `fork-*` tags remain
available; the new `v*` tag starts the Tsuzunowa-named release sequence.

## Changes since fork-0.2.0-alpha.1

- Adopt Tsuzunowa display names in app titles, sign-in/recovery screens, default
  server names, new welcome content, emails and desktop packaging labels.
  Existing user-authored content and configured server names are preserved.
- Use the approved two-notebook / circular binding-ring icon for the shared UI,
  favicon, PWA, desktop icon containers and mobile source assets.
- Adopt the E2 Fraunces 500 wordmark as SVG outlines. It renders without an
  installed font or a network font request. Normal application text is unchanged.
- Generate platform assets from checked-in SVG sources, keep maskable/adaptive
  icons within their safe area, and prevent old postinstall assets or the old
  logo animation from restoring/recoloring the previous mark.
- Use a single Web installation manifest and preserve the desktop preview's
  existing `appData/Colanode` profile directory.

The sharing, Space saved-view/filter and Notion migration features from
[the previous release](fork-0.2.0-alpha.1.md) are retained. This update adds no
database migration and does not change sharing permissions, document storage,
attachment storage or the dependency lockfile. The database remains at schema 34.

## Install locally

```sh
git clone --branch v0.2.0-alpha.2 https://github.com/hogawish/tsuzunowa.git tsuzunowa
cd tsuzunowa
docker compose -p colanode-fork-preview -f hosting/docker/fork-preview.yaml up -d --build
```

Open http://localhost:4000 and enter http://localhost:3000/config in **Add a
server**. This example binds to loopback and builds the Web and API locally.
There are no new native installers or prebuilt container images in this release.
The attached brand kit contains artwork, not application binaries.

## Upgrade and rollback

Use the same Compose project name and configuration as your existing preview.
Back up the database and uploaded files together before upgrading; retain your
custom server configuration. The paired-backup procedure in the
[previous release notes](fork-0.2.0-alpha.1.md#upgrade-from-fork-010-alpha1)
also applies. Do not remove the existing volumes.

From the existing checkout, after recording and backing up its current state:

```sh
git fetch origin --tags
git switch --detach v0.2.0-alpha.2
docker compose -p colanode-fork-preview -f hosting/docker/fork-preview.yaml up -d --build
```

Reload the Web app, then check an existing page and attachment. An installed
PWA or OS shortcut may retain cached names/icons until its metadata refreshes.
To roll back from this release to `fork-0.2.0-alpha.1`, use that previous source
tag and rebuild against the same schema-34 data and volumes. This release adds
no schema change. Keep a current backup and verify that the previous Web/API
pair can read the data before resuming writes. Upgrades from `fork-0.1.0-alpha.1`
still require the schema-32-to-34 procedure in the previous release notes.

## Validation and limits

- Shared UI TypeScript and Web production builds pass; changed TypeScript files
  pass ESLint. Naming changes also include startup-recovery and desktop-profile
  regression checks.
- The icon matches the approved SVG raster; ICO/ICNS embedded PNG frames decode
  at the expected sizes, and adaptive foreground fits its safe area.
- A fresh isolated browser renders the built Web icon and outlined wordmark in
  light/dark themes; the wordmark fits a 390px viewport.
- Prior sharing/migration integration, large Notion ZIP and paired restore
  results remain recorded in [release readiness](../release-readiness.md).
  These historical results are distinguished from the branding-specific checks.
- Native desktop/mobile installers, OS icon selection and existing installed-PWA
  metadata refresh are not validated by generating the platform assets.
- Notion ZIP migration is not continuous sync or full-fidelity interchange.
  CSV properties become text; views, relations, formulas, permissions and history
  are not recreated. Native inline/media placement is controlled by Notion's
  importer. Direct Notion copy remains experimental.
